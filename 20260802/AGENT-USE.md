# AGENT-USE.md — 大项目工程化开发中 AI Agent 的分阶段使用流程与方法论

> 面向「用 AI Agent 做真实大项目」的完整操作手册：如何在不同阶段差异化选择不同能力等级的模型，形成**低成本、高质量**的工程化闭环。
> 示例模型以 DeepSeek 系列为主（`deepseek-v4-pro` / `deepseek-v4-flash`）。

---

## 0. 核心理念（一句话）

> **让「最聪明的模型」负责想清楚，让「最快的模型」负责写出来，再让「最聪明的模型」负责挑毛病。**

大项目 ≠ 一次对话写完。它是一个**多阶段、多模型、可回环**的工程过程。每个阶段对模型能力与成本的要求不同，因此应该**按阶段切换模型**，而不是从头到尾用同一个。

### 完整闭环总览

```mermaid
flowchart LR
    A[① 需求提出<br/>+ 提示词优化<br/>flash/pro 均可] --> B[② PLAN 规划<br/>pro 级推理模型]
    B --> C[③ EXECUTE/BUILD 执行<br/>flash 级快速模型]
    C --> D[④ REVIEW & TEST 审查<br/>pro 级推理模型]
    D -->|发现缺陷| C
    D -->|通过验收| E[交付 / 迭代下一模块]
    E --> A
```

> 关键点：阶段 ④ 发现问题后**回到阶段 ③**（而非重做全部），形成「规划 → 构建 → 审查 → 修复」的内循环。

---

## 1. 需求提出与提示词优化（Requirement & Prompt Optimization）

### 1.1 目的

把「模糊的想法」变成「机器可执行的精确需求」。大项目失败的第一大原因不是模型不够强，而是**需求本身没讲清楚**。

### 1.2 输入与产出

| 项 | 内容 |
|----|------|
| 输入 | 原始需求（通常是一段口语化、有歧义的自然语言） |
| 产出物 | 一份结构化的 `PROMPT`：明确目标 + 输出范围 + 具体约束 |
| 模型类型 | 任意可用模型（flash 级即可，成本低） |

### 1.3 操作步骤

1. **清晰、结构化地提出原始需求**：
   - 是什么（项目/功能一句话定位）
   - 给谁用（目标用户）
   - 要解决什么（核心问题）
   - 技术栈倾向（可选）

2. **使用提示词优化器对原始需求进行精准化处理**
   工具推荐：[提示词优化器](https://prompt.always200.com/#/basic/user)

   优化器会帮你补全三类信息：
   - **明确目标**：把「做一个聊天工具」→「做一个 BYOK 简易聊天控制台，用户配置三项参数即可连接任意 OpenAI 兼容服务」
   - **界定输出范围**：明确「做什么 / 不做什么」（如：去除用户系统、插件、多模型管理）
   - **添加具体约束**：如「前端可部署至 Vercel」「后端逻辑集成其中」「支持流式响应」「历史存 localStorage」

3. **人工复核**：优化结果仍需开发者确认，避免过度膨胀或偏离本意。

### 1.4 检查清单

- [ ] 一句话能说清「这是什么」
- [ ] 明确列出了「边界 / 不做什么」
- - 包含 2–5 条可验证的硬性约束
- [ ] 产出的 PROMPT 可直接交给下一阶段模型执行

## 2. 规划阶段（PLAN）

### 2.1 目的

在写任何代码之前，先让模型产出一份**详细的技术实现方案**，作为后续所有编码的「施工图纸」。

> ⚠️ **禁止跳过规划直接执行。** 大项目一旦跳过 PLAN，极易出现模块边界混乱、技术选型反复、返工严重。

### 2.2 输入与产出

| 项 | 内容 |
|----|------|
| 输入 | 阶段 1 优化后的 PROMPT |
| 产出物 | 一份 `PLAN.md`：模块拆分 + 技术选型 + 任务优先级 + 实施顺序 |
| 模型类型 | **pro 级推理模型**（如 `deepseek-v4-pro`） |

### 2.3 PLAN 必须包含的内容

1. **模块拆分**：将大项目拆为可独立开发的小模块，明确每个模块的职责与边界。
2. **技术选型**：为每层（前端/后端/存储/部署）选定具体技术并说明理由。
3. **任务优先级**：区分 P0（核心必经）/ P1（重要）/ P2（锦上添花）。
4. **实施顺序**：给出里程碑（M1 → M2 → …），说明依赖关系（如：先状态层，再后端代理，再 UI）。
5. **关键代码片段**：对最核心的逻辑（数据流、错误处理、边界条件）预先给出实现草案。

### 2.4 示例结构（实际项目）

```
PLAN.md
├── 1. 项目概述与目标
├── 2. 项目结构设计（目录树）
├── 3. 前端路由与组件划分
├── 4. API 调用封装（错误处理 + 超时机制）
├── 5. 数据存储方案
├── 6. Vercel 部署配置
├── 7. 开发里程碑（M1~M9）
├── 8. 关键实现代码片段
└── 9. 测试与验证清单
```

### 2.5 为什么用 pro 级模型

规划是**推理密集型**任务：需要权衡取舍、预见边界、设计数据流。pro 级模型在此类「想清楚」任务上的质量差异，会直接决定后续执行阶段返工量的大小——**这里多花几分钱，后面省几小时**。

## 3. 执行与构建阶段（EXECUTE / BUILD）

### 3.1 目的

按 PLAN 分模块、分里程碑，把设计图变成真实可运行的代码。

### 3.2 输入与产出

| 项 | 内容 |
|----|------|
| 输入 | 已确认的 `PLAN.md` |
| 产出物 | 各模块的源码 + 可运行的本地环境（能 `npm run dev` / 构建通过） |
| 模型类型 | **低成本、高速度的 flash 级模型**（如 `deepseek-v4-flash`） |

### 3.3 操作要点

1. **按模块执行**：每次只做 PLAN 中的一个模块/里程碑，做完即验证。
2. **频繁验证**：每完成一个模块就构建/运行一次（`npm run build`），尽早暴露问题，避免最后一次性爆雷。
3. **保持上下文连续**：执行阶段通常需要多轮对话，建议按模块开新会话并附上 PLAN 相关章节，避免上下文过长导致漂移。
4. **控制成本**：编码是「大量重复 + 局部细节」任务，flash 级模型速度更快、成本更低，质量足以胜任。
5. **遇到架构级问题再升级**：若执行中遇到需要重新设计的数据流或边界决策，**暂停**，把问题交回 pro 级模型决策后，再回到 flash 继续写。

### 3.4 为什么用 flash 级模型

编码阶段 token 消耗量通常**远大于**规划与审查阶段。用 flash 级模型能把单位成本降到 pro 的若干分之一，同时交付速度更快。质量上的轻微差距，由阶段 4 的 pro 级审查来兜底。

---

## 4. 审查与测试阶段（REVIEW & TEST）

### 4.1 目的

代码全部构建完成后，**重新调用高级模型**对整个项目做严格 Code Review 与系统性测试，保证交付质量。

### 4.2 输入与产出

| 项 | 内容 |
|----|------|
| 输入 | 阶段 3 产出的完整代码仓库 |
| 产出物 | Review 报告（问题清单 + 修复建议）+ 已修复/已验证的最终代码 |
| 模型类型 | **pro 级推理模型**（如 `deepseek-v4-pro`） |

### 4.3 审查必须覆盖的四个维度

| 维度 | 检查项 |
|------|--------|
| **静态质量审查** | 代码规范、命名一致性、重复代码、模块边界、可读性 |
| **潜在 Bug 扫描** | 空值/越界、竞态条件、异步错误处理、内存/引用泄漏、类型安全 |
| **性能评估** | 有无明显性能瓶颈、是否过度渲染、流式/大请求场景是否合理 |
| **最终验收** | 是否满足 PLAN 的全部功能点与约束、边界用例是否覆盖、是否可部署 |

### 4.4 操作流程

1. 将完整代码一次性交给 pro 级模型做全面 Review。
2. 让模型输出**结构化问题清单**：`严重程度 + 文件位置 + 问题描述 + 修复建议`。
3. 针对问题：P0（阻断性）立即修复；P1 按优先级处理；P2 记录待办。
4. 修复后**再跑一轮验收**（回到流程起点，确认闭环）。
5. 通过验收后，更新文档（README / USER-SETUP 等），完成交付。

### 4.5 为什么又用回 pro 级模型

找 Bug、挑毛病、评估质量是**深度推理**任务，flash 级模型容易「自我感觉良好」漏过隐患。pro 级模型在此处能显著提升交付质量，属于**高价值的关键投入**。

## 5. 最佳实践说明（以 DeepSeek 系列为例）

### 5.1 模型分档与选型

| 档位 | 代表模型 | 特点 | 适用阶段 |
|------|----------|------|----------|
| **Pro 级（推理）** | `deepseek-v4-pro` | 强推理、强规划、强审查，成本较高、速度较慢 | ② PLAN、④ REVIEW & TEST、架构级决策 |
| **Flash 级（速度）** | `deepseek-v4-flash` | 低成本、高速度，适合大量生成 | ③ EXECUTE/BUILD、1️⃣ 需求初步整理、日常小任务 |

### 5.2 同一项目如何差异化选型（完整示例）

以「构建一个 BYOK 聊天控制台」为例：

| 阶段 | 模型 | 做什么 | 为什么 |
|------|------|--------|--------|
| 1️⃣ 需求优化 | flash | 把模糊需求整理成结构化 PROMPT | 简单改写，无需深度推理 |
| 2️⃣ 规划 | **pro** | 产出 PLAN.md（模块/选型/里程碑/代码草案） | 需要权衡与预见，质量决定返工率 |
| 3️⃣ 执行 | **flash** | 分模块写代码、跑通构建 | 编码量大，省成本、提速度 |
| 4️⃣ 审查 | **pro** | 全量 Code Review + Bug 扫描 + 验收 | 深度推理找隐患，保障质量 |
| 修复回环 | flash | 按问题清单修复 | 局部修改，速度优先 |
| 复验 | pro | 确认修复无回归、通过验收 | 最终把关 |

### 5.3 形成工程化闭环的关键

```
低成本 ─────────────────────────────► 高质量
   │                                    ▲
   │  flash 负责「写得多、写得快」          │  pro 负责「想得清、查得严」
   ▼                                    │
   └────── 规划先行 · 分模块执行 · 审查兜底 ───┘
```

1. **规划先行**：没有 PLAN 不动工。
2. **分模块执行**：flash 逐模块落地，边写边验证。
3. **审查兜底**：pro 全量把关，缺陷回环修复。
4. **按量付费思维**：把昂贵推理花在「决策点」，把廉价生成花在「执行量」上，从而在总成本与总质量之间取得最优平衡。

## 附录：阶段速查表

| 阶段 | 目标 | 模型档位 | 关键输入 | 关键产出 | 是否允许跳过 |
|------|------|----------|----------|----------|:---:|
| ① 需求优化 | 把想法变需求 | flash / pro 皆可 | 原始需求 | 结构化 PROMPT | 否 |
| ② 规划 PLAN | 出施工图纸 | **pro** | PROMPT | PLAN.md | **否（禁止）** |
| ③ 执行 BUILD | 写代码跑通 | **flash** | PLAN.md | 可运行源码 | 否 |
| ④ 审查 TEST | 把关质量 | **pro** | 完整代码 | Review 报告 + 验收 | 否 |
| 修复回环 | 修复缺陷 | flash | 问题清单 | 修复后代码 | 视情况 |
| 最终复验 | 无回归验收 | pro | 修复后代码 | 验收通过 | 否 |
